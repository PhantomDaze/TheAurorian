### 7.1 复核订正：`git diff --quiet` 的 phantom 相同项

原判定方式为：

```bash
for f in $(cat ix); do git diff --quiet 1.19.2 1.20.1 -- "$f" && echo SAME || echo DIFF; done
```

该写法存在系统性误判：**当一个路径在两棵树中都已不存在时，pathspec 匹配不到任何对象，`git diff --quiet` 仍返回 0**，于是「两树都没有该文件」被错误计为「两树逐字节相同」。这类路径称为 phantom 相同项；它只抬高「相同」数，不影响交集 450，也不影响 §7 表中「不同」的数量（137 / 76）。

独立复核（双向复现）订正如下，原数字保留以便追溯：

| 指标 | 原报 | 复核订正 | 说明 |
|---|---:|---:|---|
| 全部逐字节相同 | 313（69.6%） | **305（67.8%）** | 原报多计 8 个 phantom 路径 |
| 资源侧逐字节相同 | 291（79.3%） | **286（77.9%）** | 原报多计 5 个 phantom 路径 |

被误计入「全部 313」的 8 个 phantom 路径（1.19.2 与 1.20.1 两树均无此文件）：

- `docs/asset-remap.md`
- `docs/boss-spawner.md`
- `docs/port-plan.md`
- `worldgen/structure_set/darkstone_dungeon.json`
- `worldgen/structure_set/moon_temple.json`
- `worldgen/structure_set/runestone_dungeon.json`
- `worldgen/template_pool/runestone_bottom.json`
- `worldgen/template_pool/runestone_top.json`

其中属于资源侧（`src/main/resources` + `src/generated`）的 5 个 phantom 路径：

- `worldgen/structure_set/darkstone_dungeon.json`
- `worldgen/structure_set/moon_temple.json`
- `worldgen/structure_set/runestone_dungeon.json`
- `worldgen/template_pool/runestone_bottom.json`
- `worldgen/template_pool/runestone_top.json`

订正不翻转结论：资源侧真实收敛率 286/367 = **77.9%**，仍显著高于 Java 的 18/72 = **25%**；「资源大多可共享、Java 是版本 API 分叉，不能靠 merge 收敛」依然成立。只是原始 69.6% / 79.3% 是偏乐观值，真实收敛度略低，结论应按 67.8% / 77.9% 表述。

## 9. 解决成本评估

### 9.1 正向（1.19.2 → 1.20.1）

估算 **16–30 人时**（不含编译/冒烟验证；本任务未跑 gradle）：

- **约 20 个 Java 文件需要 1.19.2→1.20.1 API 适配**，例如：
  - `Item.Properties.tab()` 移除 → `CreativeModeTab`/`CreativeTabRegistry`；
  - `EquipmentSlot` → `ArmorItem.Type`（`ItemRegistry`/`FluidRegistry` 等）；
  - `Registry.*_REGISTRY` → `Registries.*`（`TheAurorian`、树生成器、结构类）；
  - `level` 字段 → `level()`、`DamageSource` → `damageSources()`；
  - `StructureBlockInfo` 记录访问器 `info.pos` → `info.pos()`；
  - `StructureProcessor.processBlock` 参数改为 `LevelReader`；
  - `GuiGraphics`/`PoseStack`、`HumanoidArmorLayer` 构造、`EntityType.spawn` 签名等。
- **约 26 个 Java 文件**冲突以注释/import/特性差异为主，但其中仍有真实逻辑差异（如 `CommonConfig` 的 3 个 `*_mob_density`）；另有 lang 的 `crystalline_sprite` 属资源侧差异。
- **34 个资源冲突**：26 个二进制 `.nbt` 需整文件取舍；4 个 data JSON、4 个 assets JSON 需按版本语义选择。
- **23 个 generated** 应删除后重跑 datagen，而不是手改。
- **2 个构建文件**必须保留 1.20.1 版本。
- 风险最高的 5 个结构/生成器类（`RunestoneDungeonStructure` 14 块、`MoonTempleStructure` 11 块等）可能超出估算。

> 口径说明：上文「约 20 个需 API 适配」+「约 26 个以注释/import/特性差异为主」（合计约 46 个 Java 文件）按「**解决所需工作量**」分类；§6 的「40/46 含真实代码、6/46 纯注释/import」按「**冲突块是否含真实代码**」分类。两者判据维度不同，数字不对齐属正常，并非矛盾。

### 9.2 反向（1.20.1 → 1.19.2）

估算 **2–4 人日**，且主要成本不是冲突，而是 **回滚 254 条静默自动合入**（32 个 Java 文件被改成 1.20-only API、工具链被改成 1.20.1、6 个 tag 被重命名）。这是「降级重放」，不是普通冲突解决。**不建议此方向。**

## 10. 结论

### **不可行**（作为「用 git merge 统一 1.19.2 与 1.20.1 两条线」）
### **仅部分可行**（作为「定向移植 + 版本无关资产共享」）

硬证据：

1. 两分支对应**不同 Minecraft 版本/工具链**（1.19.2+Forge 43.4.6 vs 1.20.1+Forge 47.4.10）。`build.gradle`、`gradle.properties`、`mods.toml`、worldgen JSON、注册/结构 Java 本质不同；一次 merge 只能得到服务单个版本的树，无法同时服务两版。
2. 双向冲突 **109 / 109，路径逐字节相同**；其中 **46 个 Java、34 个资源、23 个 generated、2 个构建、4 个其他（test 2、杂项 2）**。**26 个 `.nbt` 是二进制**、`.cache` 把分支名写进头、`.pyc` 被误提交——这些在原理上不能文本合并。
3. 交集 450 中 **305（67.8%）已逐字节相同**（原报 313 / 69.6%，复核订正见 §7.1）；Java 仅 **18/72（25%）**相同。两线已高度收敛，merge 主要制造版本不兼容冲突，而非带来新信息。
4. **1.19.2 独有改动中 Java = 0**。正向 merge 对 Java 的信息增量为零。
5. 非冲突自动合入 **60 vs 254** 严重不对称；反向 merge 会静默把 1.20.1 的工具链和 API 灌入 1.19.2。
6. 即使一次性解决（16–30h / 2–4 人日），后续两端每次演进都会重演同一批版本冲突，维护成本不可持续。

## 11. 若仍要推进的推荐策略

1. **不建立跨版本 merge 关系**；保持 1.19.2 / 1.20.1 / 1.21.1 三棵独立树（现行做法正确）。
2. **继续「移植式同步」**：对确认有价值的单点修复用 `cherry-pick` 或手动 port，并按 `docs/archive/` 现有流程记录（例如 `移植1.20.1审计修复.md`、`运行时缺陷修复-...md`）。
3. **抽取版本无关资产为共享源**（可选，收益最大）：
   - **可共享**：`lang`（剔除版本特有键）、`textures`/`models`/`blockstates`（用 `scripts/validate_resources.py` 门禁）、`recipes`/`loot_tables`/`tags`/`advancements`（1.19.2 与 1.20.1 均为复数目录，格式基本兼容；**1.21.1 除外**，其目录已单数化）。
   - **不可共享**：`build.gradle`/`gradle.properties`/`mods.toml`、Java 注册与结构代码、`worldgen/**` JSON、DataGen `.cache`。
   - **structures NBT**：统一由 `scripts/remap_structure_nbt.py` + `scan_structure_property_types.py` 生成并校验，避免两套二进制各自演化（当前已有 26 个 NBT 分叉）。
4. **不要用 merge 同步，改用脚本做一致性门禁**：`validate_resources.py`、NBT 扫描脚本、datagen 重跑。
5. 若确需记录血缘而不取代码：用 `git merge -s ours --no-commit`（只留祖先关系）；**不要真的解析 109 个冲突**。若坚持真实合并，只做正向（1.19.2→1.20.1），并预留 16–30h + 编译/冒烟验证预算。
